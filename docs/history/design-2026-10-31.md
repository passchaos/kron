# kron overall design

Status: design and implementation acceptance continuously updated.\
Discussion summary date: 2026-10-31.\
Target toolchain: Zig 0.16.0.

This document is the unified basis for implementation and review. It replaces
the earlier mainline idea that all asynchronous logs are formatted first and then
enter an ordinary memory queue: the final high-performance path uses
self-contained binary events, a file-backed mmap journal, background formatting,
and optional io_uring output.

This document describes the target architecture; actual APIs follow the public
modules and runnable examples, and completion evidence/remaining gaps are in the
[implementation acceptance checklist](../implementation-status.md). The initial
interface drafts below are not guaranteed to match current names exactly;
external performance numbers remain research evidence only and are not existing
kron results or guarantees.

Per later user input, asynchronous mode supports explicit ordinary memory queues
and mmap journals. Ordinary memory `accepted` does not provide process-crash
recovery; mmap remains the reliable file-logging mainline. Both share capture,
filtering, sampling, background delivery, and acknowledgement interfaces. See
[asynchronous storage](../async-storage.md).

## Current implementation scope

On 2026-10-31, the scope was single-machine logging on
Windows/Linux/macOS/Android/iOS: sync/SPSC/shared journal, text/JSON/logfmt, files
and rotation, dynamic configuration, redaction, structured fields, archives/
recovery, reliability boundaries, and performance. Network sinks and exporters
had been removed. Cross-platform status had to distinguish backend
implementation, cross-compilation, and actual device execution.

The public interface was Zig-only; all five platforms imported the same Zig
package. Application target, optimization level, and thread configuration were
passed into the library module; see [Zig package integration](../package.md).

Time handling used UTC and explicit fixed offsets and did not implement DST,
geographic timezones, or an IANA database. Readable RFC3339 time was generated
during delivery, with same-second date caches owned by the configuration
generation; events kept raw Unix nanoseconds, and monotonic clocks continued to
drive deadlines, sampling, and rotation. See [time handling](../time.md).

Single-threaded builds supported `.submission = .sync` and did not create control
or background threads during initialization. Ordinary flush, durable file
confirmation, configuration reload, and shutdown remained available;
async/SPSC returned `ThreadsUnavailable`, and deadline-aware control returned
`TimedControlUnavailable`, avoiding a blocking sink call disguised as a bounded-
time guarantee.

## 1. Goals and boundaries

### 1.1 Product goals

1. Zig-native, with structured events as first-class citizens and comptime
   validation of formats and fields.
2. Reduce application-thread logging overhead by moving number formatting, JSON
   escaping, date formatting, and file I/O to the background.
3. Produce text or JSON Lines by default, preserving `tail`, `less`, `grep`, and
   existing collection-system workflows.
4. Provide process-crash recovery on the file-logging mainline: events completely
   committed to the mmap journal can be recovered after abnormal process exit.
5. Describe behavior under process crash, system crash, power loss, disk errors,
   and overload explicitly; enqueue success must never be advertised as
   persistence success.
6. After initialization and warmup, built-in normal sync/async producer paths do
   not call the heap allocator.
7. Give every resource a budget; drops, failures, backlog, recovery, and
   persistence progress are observable.
8. Compose filters, encoders, sinks, and adapters instead of one giant Logger
   owning everything.

### 1.2 Non-promises for the first version

- Constant single-digit-nanosecond logging calls, or beating every C++ logging
  library on arbitrary hardware.
- mmap writes naturally resisting machine power loss.
- Background threads always scheduled within a specified number of milliseconds,
  or no backlog under arbitrary load.
- Automatic serialization of arbitrary pointers, object graphs, or user
  formatters with side effects.
- Multiple processes writing and rotating the same log-file set together.
- Exactly-once delivery for arbitrary sinks; the first version's crash recovery
  uses at-least-once semantics with identifiable duplicates.
- Every asynchronous request completing after successful submission; completion
  results must be checked.
- Draining the entire logging runtime safely from a signal handler.

| C++ Reckless | Deferred formatting, batched I/O, business-workload evaluation | Does not trade borrowed dynamic pointers for default-path performance |
| C++ XTR | io_uring and POSIX file backends | Backend is replaceable; benefit is decided by same-semantics benchmarks |
| Tencent BqLog | Compressed archives, different workloads, multi-platform throughput evaluation | Compressed/text throughput reported separately; different formats are not ranked together |
| Python logging | logger/filter/formatter/handler layering | Application configures the runtime; the library does not implicitly start background services |
| .NET Serilog | Enrichment, structured attributes, multiple sinks | Stable field semantics and pre-processing of sensitive fields |
| OpenTelemetry Logs data model | severity, TraceId, SpanId, scope, time fields | Borrowed for the local structured-event model |

### 2.1 How C++ performance evidence was used

- NanoLog's historical official results were about 7 ns median producer latency
  and 80M+ records/s, including binary output and offline decoding.
- fmtlog's historical official results were about 6 ns producer latency, but text
  throughput in the same table was about 3–7M records/s; its documentation
  explicitly says it cannot be compared directly with NanoLog's binary throughput.
- Quill v13 tuned-machine results had some numeric-event producer p50 around 6–8
  ns. System tuning, argument types, queue policy, and thread count all affected
  results.
- Binlog's official examples had a single integer no-clock/TSC around 8–9 ns,
  system clock around 34 ns, and strings around 38 ns; cache-cold cases were
  clearly slower.
- Reckless's performance document specifically showed the impact of queue
  saturation, business workloads, and background-thread CPU contention.

These data made the design direction worth adopting; they did not prove kron
could reach the same numbers. Frontend enqueue, text formatting, file writing,
and durable sync had to be measured separately.

## 3. Final architecture

```text
                       application thread
                              │
                    Logger / ChildLogger
                              │
           comptime filter → runtime filter → sampler
                              │
               producer redaction + typed capture
                              │
               ┌──────────────┴─────────────────┐
               │                                │
          sync submission                journal submission
               │                                │
          text/JSON encode              file-backed MAP_SHARED
               │                        self-contained records
               │                                │
               │                        background delivery thread
               │                                │
               │                    decode → Router → encode
               │                                │
               └──────────────┬─────────────────┘
                              │
                     merge complete output batches
                              │
               ┌──────────────┴─────────────────┐
               │                                │
         write/writev backend             io_uring backend
               │                                │
               └──────────────┬─────────────────┘
                              │
                       text / JSON files

  after abnormal exit: open journal → scan valid commits → replay unacknowledged events
  optional output: versioned binary archive with kroncat
```

The asynchronous producer writes directly into the file mapping. It cannot first
write to an ordinary memory queue and then have the background move records into
the journal, because that front queue remains a process-crash loss window.

### 3.1 Submission mode and output format are separate

| Submission mode | Queue/storage | Use case | Ordering and cost |
| --- | --- | --- | --- |
| sync | Calling thread encodes and writes to sink | Startup, critical errors, records needing direct error feedback | Latency includes encoding, locks, and I/O |
| async | Shared bounded mmap journal, MPSC | Default async path for ordinary concurrent file logging | Shared reservation contention; provides submission order |
| low_latency | Explicitly attached per-thread mmap SPSC channel | High-frequency, low-tail-latency logging | Per-thread FIFO; no default cross-thread total order |

text, JSON Lines, logfmt, and binary archive are output formats/sinks, not another
submission API.

The runtime never silently switches modes based on load. stdout/stderr, tests, and
fileless environments can choose sync; optional volatile async must be explicitly
labeled as not providing process-crash recovery and cannot be a hidden downgrade
of journal mode.

The earlier `async_preencoded` discussion was retained as an explicit
compatibility strategy: for custom formatting that does not fit typed capture,
the caller chooses frontend encoding and submits complete bytes directly to the
journal. It cannot secretly degrade and change the latency model.

## 4. Public interface draft

The following examples express behavioral contracts; they are not compiled code
and do not fix final factory names.

```zig
const kron = @import("kron");

var runtime = try kron.Runtime.create(allocator, init.io, .{
    .submission = .async,
    .journal = .{
        .path = "logs/app.journal",
        .max_bytes = 64 * 1024 * 1024,
        .overflow = .block,
        .recovery = .replay,
    },
    .routes = .{
        .{
            .name = "console", .format = .text, .min_level = .warn,
            .delivery = .best_effort,
        },
        .{
            .name = "file", .format = .json, .path = "logs/app.jsonl",
            .delivery = .required, .reclaim_after = .written,
        },
    },
    .file_backend = .auto,
});
defer runtime.destroy();

const log = runtime.logger(.{ .scope = "http.server" });
log.info("request completed", .{
    .status = @as(u16, 200),
    .request_id = request_id,
    .latency = kron.durationNs(elapsed_ns),
});

var thread_log = try runtime.attachThread(.{ .scope = "worker" });
defer thread_log.detach();
thread_log.infoAt(@src(), "request {d} completed", .{request_id}, .{});

try runtime.reloadFilter("info,http=debug,db.query=trace,noisy=off");
try runtime.flush(.written);
try runtime.flush(.durable);
try runtime.shutdown(.drain);
```

The first version's default journal overload policy was block to avoid silent
loss; low-latency users had to explicitly choose drop_newest and accept
count-visible loss. The specific capacity in the example was illustrative, not a
default performance guarantee.

### 4.1 Logger frontend

- `trace/debug/info/warn/err/fatal`: ordinary best-effort methods; errors go to
  statistics and diagnostic hooks.
- `tryEmit`: returns exact results for accepted, filtered, sampled, full queue,
  oversize, closing, and similar outcomes.
- `logf`: comptime format + typed arguments.
- `log`: runtime message + structured fields; dynamic string content is still
  copied.
- `infoAt(@src(), ...)`: explicitly captures the caller's source location.
- `enabled(level)`, `comptimeEnabled(level)`, and lazy APIs: decide before
  constructing expensive fields.
- `withBorrowed(fields)`: immutable derived context; the caller manages lifetime.
- `withOwned(fields)`: explicitly allocates and deep-copies context.

Ordinary Zig function arguments may be evaluated before entering the logger.
Internal filtering cannot guarantee that `log.debug(... expensive() ...)` does not
execute `expensive`; guard/lazy APIs must be used.

`fatal` only means a severity level and does not implicitly exit/abort/panic. When
drain, synchronous writing, or durable confirmation is needed, the caller chooses
it explicitly.

### 4.2 Static generics and runtime interfaces

- The typed frontend handles field validation, lightweight capture, and static
  descriptor generation.
- Encoder heavy logic is shared as much as possible to avoid copying the complete
  JSON/number formatting code into every call site.
- Runtime type-erased interfaces are used for sinks, dependency injection, and
  configuration assembly; the low-latency submission path keeps static
  specialization.
- Factories hide complex generated types so users do not write nested generic
  types by hand.

Low-latency mode provides explicit prewarm/callsite registration. Schema
registration, channel creation, first mapping, and file-space allocation are
separated from steady-state benchmarks; the first call's registration cost cannot
be hidden. Automatic registration is only a convenience path, and its cold-start
cost and capacity-exhaustion errors must be public.

## 5. Events, fields, and context

### 5.1 Event model

Metadata contains level, scope/target, event name, optional source, and format/
schema.

EventView is a borrowed view valid for the current call and contains dynamic
fields, context, trace correlation, and time. It cannot escape the logging call.

A committed journal record is self-contained and stores neither EventView nor
external object pointers. A record may contain:

- Versioned record type, total length, and sequence.
- Schema ID and schema version.
- Channel ID, channel-local sequence, and generation.
- Wall-clock time or recoverable monotonic/fast-clock mapping information.
- TraceId, SpanId, TraceFlags.
- Routing/filtering information and configuration generation decided at
  submission.
- Redacted typed payload and copied strings/bytes.
- Checksum and final commit marker.

### 5.2 Supported fields

The first version covered null, bool, explicitly sized integers, floats, enum,
error, optional, UTF-8 string, explicit bytes, timestamp, duration, and secret.
Later versions added explicit group/array and restricted object adapters.

Default capture of arbitrary raw pointers, recursive object graphs, and
user-defined formatter addresses was forbidden. User formatters can have side
effects or allocate; they were outside the built-in zero-allocation guarantee.

Field precedence: parent context < child context < current event fields. Each
final key is output once. Same-level conflicts fail at compile time when
statically knowable and fail validation for dynamic input.

JSON core metadata and attributes are separate; user fields cannot override core
timestamp/severity. Non-UTF-8, NaN/Inf, large integers, bytes encoding, and log
injection require explicit encoder policies and tests and must never produce
invalid JSON.

### 5.3 Lifetime and secret data

- Borrowed context keys/strings/bytes must remain valid until the end of each
  call.
- Owned context is deep-copied at creation and has an explicit destroy.
- Before an asynchronous call returns, dynamic strings and context values have
  been copied into the journal.
- `secret(value)` is replaced on the producer; the original never enters the
  journal, archive, or background pending buffer.
- Key-based redaction uses the configuration snapshot at submission time; the
  background cannot reinterpret old records with the current policy.
- Secrets already interpolated into a message cannot be automatically cleaned by
  field-key rules; explicit safe formatting or structured fields are required.

## 6. mmap journal and crash recovery

### 6.1 Why file-backed MAP_SHARED

Ordinary anonymous memory queues disappear with the process. A file-backed
MAP_SHARED mapping modifies file page cache; while the operating system keeps
running, completed shared-page modifications can be read again after process
exit.

This solves process-crash recovery, not kernel crash or power loss automatically.
MAP_PRIVATE, anonymous mappings, and tmpfs journals cannot be treated as durable
disk logs; journal paths and storage types must be explicit.

A local experiment wrote records to a MAP_SHARED file without msync, SIGKILLed
the child process, and the parent successfully reopened and read the file. This
proved only process-exit recovery on the then-current Linux, not power loss,
cross-platform behavior, or the complete concurrent protocol.

### 6.2 File layout

The layout is divided into:

1. File header: magic, format version, endianness, build/session identity,
   capacity layout.
2. Schema/control area: independently decodable format strings, field names,
   types, and clock mapping.
3. Channel/segment descriptor area: owner, generation, sequence, and recovery
   state.
4. Bounded data area: complete records for shared MPSC or per-thread SPSC.
5. Checkpoint area: version/sequence-validated recovery progress and durable
   watermark.

Internal capture could use native-layout optimizations, but cross-process
recovery and tool reads had to use an explicitly versioned codec. Zig struct
padding, slice layout, or raw metadata pointers could not be treated as a stable
file protocol.

A schema had to be completely committed before events referencing it could be
published. Old journals had to be independently decodable after dynamic-library
unload or a version change.

The Journal MVP shared MPSC data area used fixed slots rather than variable-length
reservations whose next boundary could not be determined. Each slot had a fixed
offset for atomic state/sequence, length, schema ID, checksum, and a fixed maximum
payload area; the slot start was computed from the file header, region base, and
slot index. A crash after reserve but before writing the header could not prevent
locating other slots.

The recovery tool enumerated all slots, validated commit, session/generation,
length, and checksum, then used sequence/checkpoint to decide replay; it did not
depend on a crashed producer's memory cursor. Safely acknowledged old records were
invalidated before reuse, and unacknowledged slots could not be reused. The schema
area similarly used independently locatable descriptors and explicit commit
states.

Fixed-slot space utilization was a known MVP cost, and `max_record_bytes` and the
actual payload distribution had to be recorded. A variable-length byte ring was a
later optimization that first required independent fixed descriptors/boundary
indexes and a recovery proof; it could not directly replace the format and break
gap recovery.

### 6.3 Commit protocol

1. Confirm space, record length, schema availability, and configuration snapshot.
2. Reserve an area not used by the consumer.
3. Write header/payload/checksum.
4. Finally publish the atomic commit state with release semantics.
5. The consumer reads after acquire confirmation; the producer cannot overwrite
   before completion.

Commit state had to be correctly aligned and include generation/sequence to
prevent a wrapped old commit from being mistaken for a new record. Recovery
scanning validated length, type, generation, and checksum and could not trust
shared cursors or magic bytes at arbitrary offsets.

Atomic release/acquire specifies concurrent memory visibility, not disk writeback
order. A durable checkpoint had to be updated only after relevant data and
metadata were persisted; if a crash interrupted sync, the commit bit could not be
used to infer durability.

Incomplete reservations, wrap markers, over-limit cases, and cancellation needed
recoverable states. During normal operation, failed reservations published
tombstones to avoid blocking the consumer.

After a process crash, the recovery tool could not stop at the first uncommitted
MPSC reservation and lose later records committed by other threads. The shared
queue format had to provide independently verifiable slots/boundaries; a
variable-length format needed reliable reservation descriptors. This was a
mandatory acceptance condition for the journal MVP.

### 6.4 Preallocation, page faults, and budgets

- Set file length and preallocate actual space where possible; ftruncate alone is
  not an actual disk-space guarantee.
- Pre-map and pre-touch pages; keep first-touch and growth off the normal low-
  latency path.
- Strictly bound total journal bytes, channel count, schema area, background
  buffers, and in-flight I/O.
- External processes must not arbitrarily truncate an active mapping, avoiding
  access beyond EOF.
- Page faults, dirty throttling, kernel writeback, and storage failures affect
  mmap tail latency; wait-free behavior cannot be claimed.
- Initialization failure returns an error. When recovery is required, the runtime
  cannot silently switch to a volatile queue.

### 6.5 Reclaim, replay, and duplicates

Records cannot be reclaimed immediately after the background reads, formats, or
submits an SQE. Reclaim waits for every required route to reach its corresponding
acknowledgement boundary.

Process-crash protection requires at least complete write success before reclaim.
Power-loss protection additionally requires output data, relevant metadata, and
checkpoints to complete durable sync per protocol; advancing only the written
watermark and overwriting the journal can break power-loss recovery.

First-version recovery is at-least-once: a crash after a successful write but
before the checkpoint update can replay duplicates. Output carries session/
channel/sequence as a stable event ID, and tools can report duplicates or perform
explicit deduplication. Exactly-once for arbitrary sinks cannot be promised.

For recoverable file sinks, later explicit offsets, output lengths, tail repair,
and checkpoint protocols can reduce duplicates. Two file updates are not
naturally atomic.

Bad records, unknown versions, or missing schemas return diagnosable errors;
corrupt tails are isolated and preserved as evidence, never silently formatted as
normal events.

## 7. Concurrency, ordering, and thread exit

### 7.1 Shared MPSC

- Suitable for ordinary Logger; does not require every short-lived thread to
  register.
- Controls acquire/release ordering for reserve/commit/reuse.
- Submission hotspots and cache-line contention must be measured; shared state is
  separated across cache lines sensibly.
- Normal consumption can use reservation order, but a preempted producer after
  reserve can cause head-of-line blocking.
- Slot ownership is not broken to bypass gaps; recovery scanning after process
  exit is a separate flow.

### 7.2 Per-thread SPSC

- `attachThread()` obtains a fixed-budget channel; `detach()` explicitly retires
  it.
- Write and read cursors are separated onto appropriate cache lines.
- Producers do not perform a global fetch-add per event; statistics accumulate
  per channel and are summarized later.
- The consumer fairly polls or drains in bounded batches so high-frequency
  threads do not starve low-frequency threads.
- After detach, the channel remains until the consumer drains it, then is
  reclaimed.
- Thread death is never guessed through TLS destructors or heartbeats.
- A channel that misses detach remains owned by the runtime, and the attachment
  leak is reported; shutdown only drains and invalidates, without freeing a
  control block still reachable by an old token.

An SPSC token may submit only from the thread that created it; it cannot be copied
to multiple producers or used after task migration. Explicit Context can cross
threads; channel tokens cannot.

A token stores a stable control block and generation; emit/detach first check
runtime state and generation, then access the data area. A token used after
detach, or a stale token after pool reuse, is rejected and cannot access the new
channel. The control block remains at a valid address for the runtime lifetime; a
late detach after shutdown is handled safely. Final release happens only after
destroy preconditions are met; token-reachable objects cannot be freed merely
because the worker joined.

### 7.3 Ordering

- sync: each output record is not interleaved; locks...
- shared async: reservation/delivery order, without a wall-clock total order.
- SPSC: per-thread FIFO, with no default cross-thread total order.
- An optional timestamp merge approximates ordering only within an explicit grace
  window and cannot claim causal total order.
- An optional global sequence reintroduces shared atomic hotspots and gap waits
  and must be measured separately.

## 8. File output and io_uring

### 8.1 Common basis

The background first generates complete text/JSON records, then merges batches.
Text/JSON encoders and I/O backends are decoupled.

Two backends:

- portable: batched write/writev or standard-library equivalents.
- linux_uring: preallocated buffer pool, batched SQEs, CQE completion handling.

`.auto` only performs capability/configuration selection at initialization; the
default preference for io_uring is decided by same-semantics benchmarks. With
in-flight I/O present, the backend cannot be changed without draining.

The mmap journal producer store does not need an extra write. io_uring accelerates
background output and file-sync requests; it does not replace the journal commit
protocol.

### 8.2 Why not use io_uring unconditionally

Batched write/writev already amortizes syscall cost. For single-file sequential
writes, low log volume, or formatting-bound workloads, SQ/CQ management may have
no net gain. io_uring is suitable for overlapping encoding and I/O, multiple file
outputs, and sustained high throughput.

Buffered file writes still use page cache, and registered buffers are not zero-
copy. SQPOLL, O_DIRECT, huge queues, and many pinned buffers are not default
conditions; each must be profiled and tested.

### 8.3 Correctness contracts

- A single background owner assigns explicit file offsets and does not rely on a
  shared implicit file position.
- A buffer can be reused only after its CQE arrives and is acknowledged.
- Negative results, short writes, and zero progress are checked; a batch is not
  written until short writes complete.
- Completions may arrive out of order; only the contiguous successful output
  watermark advances, and a trailing success cannot be mistaken for filling an
  earlier gap.
- flush waits for the target range to be completely written; durable additionally
  waits for correctly ordered fsync/fdatasync completion.
- Submitting fsync after multiple writes does not naturally guarantee
  dependencies; use completion barriers or a verified link/drain protocol.
- Rotation, close, cancellation, and shutdown must handle in-flight I/O lifetime.
- On file write failure, the journal not yet safely reclaimed is preserved and
  the runtime enters an explicit backpressure/failure state.

The backend maintains a `user_data → operation state` table recording batch,
buffer, file generation, journal range, original SQE, and cancellation SQE state.
A successful cancel CQE does not mean the original request is finished; the
original success, error, or ECANCELED CQE must still be reaped. Short-write
resubmission forms a child-request chain within the same logical batch, and the
written watermark does not advance until all bytes succeed.

Operation IDs cannot be reused while old completions may still arrive. Buffers,
registered buffer/file slots, file close, and related journal reclaim must wait
for the original/resubmitted requests referencing them to finish; the cancel
request's own completion must also be reaped before destroying operation state.
shutdown/deinit cannot infer safe resource release from cancelling submitted
requests.

Initial benchmarks compared 64/128/256 KiB batches and queue depths 1/4/16,
reporting CPU, latency, memory, completion throughput, and durable cost; these
were test parameters, not promised optimal configurations.

## 9. Dynamic filter and configuration

### 9.1 Environment variables

```bash
KRON_LOG='info,http=debug,db.query=trace,noisy=off' ./app
```

- A level without a target is the default rule.
- `scope=level` is a namespace override.
- Longest namespace match wins, by component boundary: `http` matches
  `http.client`, not `httpx`.
- Repeated scopes: later rules override earlier ones.
- off disables the corresponding scope.
- Each named route can have independent rules; configuration files/APIs support
  route-level filters.

Environment variables are read at application startup. Exporting in another shell
does not change an already running process. Runtime changes go through `setLevel`,
`reloadFilter`, application management interfaces, or configuration-file reload.

Default configuration-source priority: library defaults < application config file
< environment variables < explicit application overrides. Runtime APIs are
explicit new configuration transactions; old environment variables cannot
periodically overwrite them silently. Applications may choose a different
priority but must declare it explicitly.

### 9.2 Hot path and configuration publication

1. Reload parses and validates the complete configuration in a thread context.
2. Generate an immutable snapshot and generation.
3. Publish atomically.
4. Reclaim old snapshots safely through reference counting/epochs or similar.

The hot path does not read environment variables, parse rules, or hold a global
configuration mutex. A simple global level uses an atomic value; per-scope/route
results may be cached and refreshed when the generation changes.

Cache keys must distinguish runtime, scope/callsite, and generation; one global
static callsite cache cannot contaminate different loggers. Coarse early level
filtering must account for all routes/overrides and cannot drop `http=trace`
events because the global level is info.

New calls after a successful reload use the new rules; calls already started may
finish with the old snapshot they obtained. Every event's filter/redaction/route
decision comes from one consistent snapshot.

Accepted records are delivered according to the decision at submission; the
background cannot re-drop old records with the latest filter. A recoverable
journal stores necessary route identifiers and decisions, not merely an in-process
old-snapshot pointer.

First-version hot reload only adjusts filter/level policies that do not change
resource ownership. If sink/route hot replacement is supported later, the old
route must remain valid until its accepted records complete; the journal stores a
stable route ID and necessary file-recovery information. Custom sinks are bound by
the application to a cross-restart ID; missing bindings report undelivered records
and preserve the journal rather than silently forwarding to a new target or
reclaiming.

### 9.3 Compile time and complex filtering

Debug/trace callsites removed at compile time cannot be re-enabled at runtime.
Builds needing field diagnostics should keep the corresponding callsites.

Level/scope is the first version's common filtering. Field predicates, message
matching, and regex are later extensions; every filter deciding delivery must run
before journal commit/acceptance. Rules requiring formatting first force the user
to choose the explicit frontend-preencoding strategy and bear the cost; deferred
background work cannot revoke acceptance.

Background query/display filtering is for tool views or separately declared query
interfaces, not delivery filters, and does not reduce accepted/written delivery
requirements.

Invalid configuration is rejected as a whole with a specific location and reason;
the old configuration is preserved and nothing is partially applied. A SIGHUP
handler only notifies the configuration thread; it cannot parse, allocate, or
reload inside the signal handler.

## 10. Reliability, flush, and shutdown

### 10.1 Completion boundaries

| Boundary | Meaning | Does not mean |
| --- | --- | --- |
| accepted | Accepted under current policy; in journal mode the self-contained record is completely committed | text/JSON written or file durable |
| written | Corresponding output bytes completely written, no longer only in user-space writer buffers | Resistant to system crash/power loss |
| durable | Required data, metadata, and checkpoints completed platform-defined synchronization | Lossless under arbitrary hardware failure |

If a volatile mode exists, its accepted only means ordinary memory enqueue and
must be separately declared as lacking journal recovery.

`flush(.drain)` waits for target accepted records to be processed by the
background; `flush(.written)` additionally waits for writers and in-flight output;
`flush(.durable)` waits for file persistence and checkpoints. Drain itself cannot
reclaim journal records not yet written.

A sink declares which acknowledgement capabilities it supports. stdout/stderr
written means successfully handed to the corresponding descriptor; custom sinks
need their own confirmation contract. A route not supporting durable must return
`UnsupportedDurability` or be explicitly excluded by the caller; ordinary flush
cannot be treated as durable success.

Routes explicitly declare required/best_effort and the written/durable boundary
required for journal reclaim. Each required route maintains its own acknowledgement
watermark; an event is reclaimable only after all required routes selected at
submission meet their requirements. best_effort route failures may be counted but
do not indefinitely block journal reclaim for other routes.

A flush without specified routes applies to all required routes by default; if
any route does not support the requested capability, the whole call returns an
explicit error rather than silently skipping. The API also provides explicit
route sets. In the example, console is best_effort and file is required, so
flush(.durable) confirms file and related durable checkpoints without promising
console durability.

If accepted events must also be replayable after power loss, the corresponding
required route's `reclaim_after` must be durable, or an equivalent protocol that
retains a persistent journal copy is required. The journal cannot be overwritten
after written only while promising power-loss losslessness for events not
confirmed durable.

### 10.2 Flush snapshot

- MPSC uses an explicit target reservation/commit barrier, including producers
  already submitting.
- SPSC `flushThread` publishes a local channel barrier and waits for ack.
- `flushAll` snapshots committed channel positions under a registry generation
  and waits for the background delivery thread to pass the target.
- New events after the snapshot are not part of this flush.
- The admission/in-flight mechanism defines the linearization boundary for
  cross-thread flush; "the queue looks empty" is not completion.
- A background delivery thread calling blocking flush itself returns an explicit
  error to avoid self-deadlock.

### 10.3 Shutdown

State machine: running → closing → closed.

1. Close new attach and new event admission.
2. Wake producers waiting under block policy.
3. Wait for current in-flight producers to finish or publish an identifiable
   abort state.
4. Drain active/retiring channels.
5. Complete target outputs, sync policy, and checkpoints.
6. Reclaim in-flight I/O and join workers.
7. Enter closed and report undelivered counts and errors.

shutdown is idempotent. A deadline return does not mean memory used by threads/I/O
can be released immediately; after a timeout resources remain valid until the
operation truly stops or the caller exits the process.

destroy may be called only after all logger/token users have stopped using it
concurrently. The runtime has a stable address after startup and cannot move
objects still referenced by workers.

### 10.4 Process crash and power loss

- Normal exit: drain + written/durable per configuration.
- SIGSEGV, abort, SIGKILL: rely on journal scanning; do not depend on exit codes
  or a crash handler.
- System crash/power loss: only the successfully confirmed durable watermark is
  promised; written/accepted may not survive.
- For newly created or rotated files, directory entries, file length, and
  necessary metadata synchronization are part of the durable protocol.
- If the journal itself has a storage error or corruption, report the failure;
  losslessness is not promised.

## 11. Backpressure, sampling, and health

### 11.1 Overload policy

- block: wait for space, preserve acceptance semantics, but latency no longer has
  a low upper bound.
- drop_newest: reject the current event with exact counts; for low-latency
  scenarios explicitly allowing loss.
- fallback_sync: explicit synchronous write; may pass older queued events, with
  ordering changes documented.
- drop_oldest: not implemented in the first version, avoiding overwriting data
  used by consumers/in-flight I/O.

Oversized records use drop or explicit synchronous/preencoded fallback. The
result must be `dropped_oversize`; a half JSON record is never emitted.

Sampling runs before capture; default critical levels may bypass it, but level
cannot replace audit-reliability requirements. Later versions implement
deterministic count sampling, token bucket, and rate limiting.

### 11.2 Results and statistics

Producer results and delivery results are counted separately so accepted is not
mistaken for successful writing.

- Producer: accepted, filtered, sampled, dropped_full, dropped_oversize,
  rejected_closing.
- Delivery: written, durable, write_errors, sync_errors, recovered,
  replay_duplicates, corrupt_records.
- Resource: journal backlog bytes/records, oldest age, high-water mark, channel
  count, in-flight I/O, worker state.
- Diagnosis: first/last error, last written/durable time and watermark,
  configuration generation.

Statistics use per-channel counters where possible to reduce global cache-line
contention. After drop recovery, the background delivery thread may generate a
summary loss record rather than recursively logging every drop.

Error hooks are non-recursive and rate-limited, and do not call user code while
holding sink locks. kron must not use `std.log` to write back into the same kron
runtime internally.

## 12. Encoding, file rotation, and tools

### 12.1 Output formats

- text: human-readable, control characters correctly escaped, color only for
  explicit terminal output.
- JSON Lines: one valid complete JSON object per line, preserving original typed
  attributes.
- logfmt: added later with fixed escaping rules.
- binary archive: optional long-term storage sink preserving schema and complete
  events, with a separate retention budget.

Normal file errors may already have caused OS-level partial writes, so "complete
record" means not voluntarily submitting half an encoder result; file recovery
must detect and repair corrupt tails and cannot promise that hardware errors never
leave half a line.

### 12.2 Rotation

The first version used size + retention; time rotation and external reopen came
later.

- Rotate only at complete output batch/record boundaries.
- A single oversized event is not arbitrarily split; explicit configuration may
  allow an oversized single file or reject the event.
- Wait for old-file in-flight writes to complete before closing.
- rename/delete/sync failures are diagnosable and never delete the only recovery
  copy.
- Multiple processes rotating the same set concurrently are unsupported.

### 12.3 kroncat draft

```bash
kroncat app.kron
kroncat --follow app.kron
kroncat --level warn app.kron
kroncat --where 'request_id == "abc"' app.kron
kroncat --json app.kron
kroncat --recover app.journal
```

The tool reads versioned schemas and records, supports valid commit boundaries,
bad-tail diagnosis, and recovery reports. It cannot require the old application
binary or pointers into an old address space to decode.

Live follow shows completely committed events by default and does not describe
them as durable. Binary archive is an explicit user choice; ordinary text/JSON
viewing does not depend on kroncat.

## 13. Clocks, trace, and std.log adaptation

- Wall time uses `std.Io.Clock.real`; deadlines, elapsed time, and sampling
  periods use a monotonic clock.
- Timestamps are a configurable cost; not every record formats a date or
  symbolizes a stack by default.
- Optional TSC/hardware fast clocks require platform capability, calibration,
  cross-core, and virtualization verification; the journal must hold recoverable
  mapping information.
- A path that re-reads a monotonic clock per record cannot be advertised as a TSC
  nanosecond result.
- Source uses explicit `@src()`; `@src()` inside an ordinary function does not
  represent the external call site.
- TraceContext explicitly carries TraceId/SpanId/flags; lightweight Span came
  later.
- The `std.log` bridge is configured by the application root module through
  `std_options.logFn`, mapping four standard levels and scope.
- The bridge cannot replace `std.options.logFn` at runtime; dynamic adjustment
  targets the runtime filter it binds.
- Unbound, shutdown, and error paths must not recursively call the same logging
  bridge.

## 14. Module structure and dependencies

```text
src/
  root.zig
  core/        level, field, event, logger, context, runtime
  config/      parser, filter, snapshot, reload
  submit/      sync, capture, callsite, thread_channel
  journal/     format, schema, mmap_store, commit, checkpoint, recovery
  pipeline/    route, router, sampler, redact
  encoder/     text, json, logfmt
  sink/        interface, writer, file, rolling_file, multi
  backend/     portable, linux_uring, buffer_pool
  platform/    io, mapping, clock
  telemetry/   trace_context, span
  adapters/    std_log
tools/
  kroncat
tests/
  compile_fail, crash, fault, integration
bench/
  producer, encode, output, end_to_end, business_workload
docs/
  design.md
```

The typed frontend depends on core/config/submit; capture depends on journal
codec; background depends on pipeline/encoder/sink; sink depends on backend/
platform. Sink and the lower-level journal do not depend back on Logger, avoiding
recursion and circular dependencies.

`root.zig` maintains a stable public export surface and does not directly expose
all internal implementation. Modules are split by stable responsibility, heavy
logic stays shared, and file growth/callsite code explosion are avoided.

Zig 0.16 platform constraints:

- Receive `std.Io` explicitly.
- Use `std.Io.Mutex/Condition`, not the old `std.Thread.Mutex`.
- Writers accept `*std.Io.Writer`; concrete file writers preserve underlying
  errors.
- `std.os.linux.IoUring` provides write/writev/fsync and buffer/file registration
  interfaces.
- Mapping, sync, file metadata, and thread interfaces are isolated; unsupported
  platform capabilities return explicit errors or select an authorized mode.
- Windows/Linux/macOS/Android/iOS use the same event and journal protocol; Linux,
  Windows, and Darwin provide independent file-mapping backends. Actual recovery
  and durability qualification on other platforms is declared only after
  device-specific testing; see [platform support](../platforms.md).

## 15. Verification and performance gates

### 15.1 Correctness

| Scope | Core tests |
| --- | --- |
| Fields/comptime | Supported types, optionals, enum/error, invalid pointers, duplicate keys, invalid formats |
| Encoder | Goldens, control characters, UTF-8, NaN/Inf, integer boundaries, parseable JSON per line |
| Context | Parent/child override, owned deep copy, source-slice overwrite after submission does not change output |
| Redaction | Secrets never enter journal, field-policy snapshots, explicit message boundaries |
| Allocation | Counting or failing allocator verifies built-in hot paths after initialization/warmup |
| Journal | reserve/commit/reuse, generation, wrap, schema ordering, capacity boundaries |
| Crash | SIGKILL injected at every commit/checkpoint/I/O step; complete events recover |
| MPSC gaps | One producer reserves and stops; later committed events still recover after crash |
| Concurrency | 1/N producers, no duplicate corruption, SPSC thread ownership, detach/shutdown |
| I/O faults | Partial/zero writes, ENOSPC, sync errors, out-of-order CQEs, rotation failures |
| Filter | Longest scope, component boundaries, route union, atomic reload, old-event decisions |
| Flush | Snapshot boundaries, concurrent flush, in-flight writes, durable dependencies |
| Shutdown | Block wakeups, double shutdown, resources valid after deadline, worker self-lock |
| Recovery tools | Decoding without old binary, unknown schema/version, bad tail, duplicate reports |

SIGKILL tests are not power-loss tests. Durability guarantees require dedicated
verification through virtual-machine/block-device fault injection, with the
filesystem, kernel, and storage configuration recorded.

### 15.2 Performance

The following must be reported together:

- Producer latency: p50/p99/p99.9, with single-record and batch-average
  measurements separated.
- Encoding throughput: text/JSON with field counts and string sizes.
- Written throughput: includes final drain, not only time to submit into a fast
  queue.
- Durable throughput/latency: sync policy measured independently.
- Saturation: actual acceptance, drops, blocking time, backlog age, and recovery
  volume.
- Business impact: application throughput, CPU, cache misses, and scheduling
  contention compared with a no-logging baseline.
- Resources: journal bytes, per-thread channels, backend buffers, binary size, and
  compile time.

Scenarios include filtered, 0/5/10 fields, numbers/short strings/long strings,
1/4/16 producers, warm/cold cache, burst/sustained overload, slow/failing sinks,
frequent thread creation/destruction, reload, and rolling.

When comparing kron with spdlog, Quill, fmtlog, NanoLog, Binlog, and similar
libraries, keep the message, output format, clock, queue/memory budget, drop
policy, final drain, and durability boundary fixed. Tests that cannot be aligned
are reported separately; binary throughput cannot be used to rank text output.

Baseline goals: built-in hot paths make zero allocator calls; scope filtering is a
small number of atomic reads/comparisons in steady state; a low-latency producer
does not format, perform per-record system calls, or contend on a global
submission lock. Mmap faults and backpressure costs are reported separately.

Absolute nanosecond/throughput targets are established on fixed machines after
implementation. Once a stable baseline exists, use a 5%–10% regression threshold
in the same environment; noise and insufficient samples must not be mistaken for
optimization gains.

## 16. Staged delivery

1. Semantics and skeleton: freeze event, field, result, configuration, and
   reliability boundaries; establish minimal Debug/ReleaseSafe verification.
2. Synchronous baseline: text/JSON, context, redaction, filter, writer/file sink,
   fault tests.
3. Journal MVP: self-contained schema, file-backed layout, commit/generation,
   recovery tools, SIGKILL and MPSC gap tests.
4. Asynchronous mainline: shared journal, background formatting, written
   checkpoints, backpressure, flush/shutdown; the first async version with
   process-crash recovery.
5. Durable protocol: data/schema/output/checkpoint synchronization ordering and
   system-fault verification, with explicit at-least-once recovery.
6. Low latency: explicit SPSC attach/detach, static callsites, compact capture,
   per-channel stats, warmup.
7. Linux acceleration: io_uring, batched/in-flight I/O, rotation, and same-round
   portable benchmarks to choose the default backend.
8. Operations and ecosystem: complete hot reload, sampling, std.log bridge,
   flight recorder, trace adapter.
9. Optional archives: binary archive, kroncat follow/query, compression, version
   compatibility, and retention.

Implementation could first use a test memory queue to validate the codec, but an
async milestone without a journal could not be advertised as satisfying the final
crash-recovery design.
