# 就绪记录的合并交付窗口

后台按 64 条记录为一个服务量子计算队列预算，`consumer_batches_per_queue=1..4` 给出每轮最多 64–256 条的上界。现在一次 checked peek 可取出当前剩余预算内已经完整提交的连续记录，并让它们共享配置 View、输出 flush 和消费进度通知。不会等待后续 producer 来补满窗口，也不会把未完成 reservation 越过去。

假设剩余四个量子，队列已有 255 条连续记录：旧路径最多每 64 条一次 flush，新路径可在全部 255 条写出后执行一次窗口 barrier，再逐条回收。若当前只有一条，则立即交付这一条并扣除一个量子；其余三个量子最多再服务 192 条。因此 producer 在交付期间继续提交，也不能把这一轮的服务量无限延长。

默认每队列服务总上界仍为 256 条；可选预算一则仍为 64 条。将 160 条积压日志放在已经开始交付的第一条之后时，预算 1/2/3/4 的 peer 服务位置仍为 1/65/129/161。这里保证的是记录数量预算，不能保证操作系统墙钟调度上界。更大的确认窗口可能降低写入和唤醒次数，也可能改变满队列调用的分位数，需按实际负载验证。

## 写出和回收顺序

窗口中的全部记录先经过 checked peek，校验 committed 状态、长度、generation、CRC 和 schema 就绪状态。读取到后面的损坏会使整个 peek 失败；任何记录都不会进入 sink。配置按事件捕获的 generation/fingerprint 查找，每个不同版本持有独立 View，一次窗口最多包含现有配置表允许的 64 个版本。

每条事件按原来的路由输出，随后执行窗口中各配置组要求的 written/durable barrier。全部要求的屏障完成后，journal 仍逐条执行原有 `releaseAfter` 检查与回收，配置 record pin 也逐条释放；没有提前释放 accepted 记录，没有省去第二次 CRC，没有改 checkpoint 协议。

输出或 flush/sync 失败时，窗口中的记录全部保留。如果输出已完成但回收期间遇到后续损坏，只确认实际回收成功的前缀，written 计数和配置 pin 跟随该前缀更新。View 在错误展开中释放，未回收记录继续保护旧配置与资源 lease。较早记录可能已经写出而仍被保留，崩溃恢复继续采用可识别重复的至少一次语义。

## 资源与验证

记录、channel、snapshot 和边界 scratch 以固定 256 项预留在消费者栈上；配置组数组仍为 64 项。不增加 producer 工作或堆分配，也不扩大 journal、sink 和在途 I/O 的配置预算。消费者栈空间增加，具体当前目标的大小在测量证据中记录。

真实 runtime 回归覆盖 Memory/Mmap、共享/SPSC、普通/schema 八种组合，255 条就绪记录第一次 flush 时全部输出，初始化后的失败 allocator 没有新增调用。另验证：后段初始损坏为零输出；旧/新配置的 flush 或 durable 失败保留全部记录与两侧 pin；输出后的第 191 条回收损坏仅确认前 190 条，剩余 65 条继续保护旧配置。原满队列关闭唤醒、deadline 和实际文件故障测试继续执行。

此优化针对已有就绪记录的合并，不采用定时延迟填批或低频日志缓冲策略。性能证据分别比较 Memory/Mmap 和 portable/io_uring，保持完整 JSON、系统墙钟、最终 written flush、关闭与文件核验。当前阶段的原始结果见 `bench/evidence/2026-11-01-coalesced-delivery/`；性能改善不能推广到未测负载或跨库排名。
